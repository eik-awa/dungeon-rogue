## 以下、元の調査メモ(修正前の状態の記録として残す)

### S-1. 継承品が毎回復活する(実証済み・最優先)

`startFromChapter()` は継承品を消費済みにするため `meta.inherited = []` を保存するが、
その直後に呼ばれる `enterNode()` が**レンダー時にクロージャされた古い `meta`** を使って
別のフィールド(`seen`)を書き込み、結果として `inherited` を古い値で上書きしてしまっていた。

```js
// enterNode() (修正前)
{ const ns = { ...(meta.seen || {}) }; let ch = false;
  for (const e of s.enemies) { if (e.bookId && !ns[e.bookId]) { ns[e.bookId] = true; ch = true; } }
  if (ch) { const m2 = { ...meta, seen: ns }; setMeta(m2); saveMeta(m2); } }
```

**プレイヤーから見た挙動**: 「森へ入る」→ 中断してタイトルへ →「新しく始める」を繰り返すだけで、
同じ伝説武器を何度でも手に入れられる(無限増殖)。

**同じ根本原因で影響していた箇所**(全て `updateMeta()` 経由に統一して解消):
`startFromChapter` / `enterNode` / `attackWith` / `battleWon` / `finalizeDeath` / `rebirth` /
`autoCarryOverFromDeadRun` / 「やり直す」/ エンディング画面 / 報酬広告コールバック /
イベント関連 / `resolveOrbChoice` / `eventConvert` / `buySkill` / `dismissRefundNotice` /
`claimCompensationDew`。

### S-2. 宝樹の雫が自動継承の対象にならない(実証済み)

```js
// itemScore() (修正前)
if (c.kind === "meta" || c.kind === "metaHp") return 10000; // 雫・心臓は最優先
```

雫の実際の `kind` は `"orb"`。`"meta"` という kind はコード上どこにも存在しない
(タイプミスと思われる)。結果、雫のスコアは14点(ほぼ最下位)になり、死亡画面での
自動選択・自動継承(`recommendPick` を使う3経路すべて)で他の並アイテムより後回しにされていた。
継承枠が少ない序盤ほど影響が大きい(貴重な雫を毎回死なせて失っていた)。

### S-3. 章クリア画面で「中断してタイトルへ」を押すと確定報酬が消える

ボス撃破の確定ドロップ(伝説武器・苔の心臓等)保存対策(`rewardPhase`/`drops`)は
`battleWon` や debounce 保存には実装済みだったが、明示的な「中断してタイトルへ」ボタンの
直接 `saveRun` 呼び出しにはこの引数が渡っていなかった。

### S-4. 「やり直す」が中断ランを消さない

`checkpoint` を1にリセットするのに、`clearRun()`/`setSavedRun(null)` を呼んでいなかったため、
中断中の深い章のランが残り続け、タイトル画面の表示と矛盾する状態になっていた。

### A-1. 属性ごとの「余韻」(lifesteal)が全属性に乗る

`elementDmgPct` の方は `effect.element` でフィルタされているのに、対になる `lifestealPct`
(斬・魔・突・打・音の「余韻」系スキル、各4%)には `element` フィールド自体が無く、
呼び出し側(`attackWith`)もフィルタしていなかった。5種類フルで習得すると、
どの武器で殴っても常時+20%吸収が乗っていた計算になる。

### A-2. `orbBagBonus` / `orbSlotBonus` が常に0(未解決)

セーブ形式・`invCapOf()`・`effSlots` の計算まで配線は通っているが、**この値を実際に
加算するコードがどこにも存在しない**。「宝珠」のような未実装のボーナスアイテム/機能を
想定した設計の残骸と思われるが、UIからは到達できない。バグではなく未実装機能の可能性が
高いため、今回は手を付けず記録のみ残す。

### A-3. 武器スロット拡張スキルが中断ラン再開時に未反映

`buySkill()` はアクティブなラン(`g.screen === "run"`)にしか即時反映しないため、
タイトル画面でスキルを購入 → 別の中断ランを再開、という流れだと武器配列が古いスロット数の
ままだった。`resumeRun`/`warpToChapter` で `weaponSlotsOf(meta)` に合わせて配列をパディング
する処理を追加した。

### B-1. `setG(updater)` の中で副作用(`tryProceed`/`proceedLeaving`)

`nextNode()` → `enterNode()` は `Math.random()` による敵生成と `saveRun()`(I/O)を伴うため、
updater の中で呼ぶと複数回実行された場合に「画面に出ている敵」と「保存された敵」がずれる
おそれがあった。`gRef.current` から同期的に一度だけ計算する形に統一した。

### B-2. `committed` パターンによる報酬・保存スキップ(実証済み・最重要)

`resolveOrbChoice`/`eventConvert` は、React 18 で `setG(updater)` の updater が
同期的に実行されないことがあるという前提に反する実装になっており、**通常の1回タップで
毎回**報酬(継承枠+1 / 精の結晶+1)が付与されない不具合が実際に発生していた。
`equipItem`/`unequipWeapon`/`discardItem`/`toggleLock`/`takeDrop`系/`buySkill`(武器スロット
即時反映部分)も同型で、こちらは画面上の変化はするが保存だけが飛ぶ形で発生していた。

**注意(この修正自体が誘発した副作用)**: `updateMeta` 導入で `metaRef.current` が同期的に
最新化されるようになった結果、「放棄する」ボタンを連打したときに `autoCarryOverFromDeadRun`
が2回とも本当に効いてしまう(継承品の二重付与)という**新しい**退行が一時的に発生した
(以前は無関係な stale-closure バグが偶然この二重実行を無効化していた)。`savedRunRef` で
同一tick内の2回目を弾いて解決(`test15`)。

### B-3. ログオブジェクトの形が2種類混在

`pushLog()` は `{ text, strong, k: uid() }` 固定だが、`resolveOrbChoice()` だけ
`{ id, text, hi }` という別形式を使っていた。描画側は `key={l.k}` / `l.strong` を見るため、
雫のログだけ key が undefined になり、React の重複キー警告が出ていた。`pushLog` 経由に統一。

### B-4. 「タイトルへ」ボタンが戦闘中(`busy`)でも押せる

中断確認ダイアログを経由するとはいえ、`busy` 中に開いた場合、確定時に読む `g` が
ターン処理の途中の不整合な値になりうる。`disabled={g.busy}` を追加。

### B-5. 広告報酬コールバックが `committed` パターンで保存スキップ(実証済み・テスト仕様書作成中に発見)

`window.__onRewardAdResult__`(雫2倍広告・広告復活)の dew/revive 分岐は、B-2 で修正した
はずの `committed` パターンと同型の実装が**未修正のまま残っていた**:

```js
// 修正前
let committed = null;
setG((s) => { if (s.rewardAdPending !== "dew") return s; ...; committed = ns; return ns; });
if (committed) flushSaveRun(committed);
```

B-2 の修正時、この関数がネイティブブリッジからの**直接関数呼び出し**(React の
SyntheticEvent ではない)であることを見落としていた。`setG(updater)` の updater は
React のイベントシステム経由の同期的な discrete update として扱われる場合にのみ確実に
即時実行されるが、`window.__onRewardAdResult__` はそのパスを通らないため、updater が
`if (committed)` の判定より後に実行される(=判定時点では `committed` が `null` のまま)
ケースが実際に発生することを、AD-02 のテスト作成時に確認した。結果、広告視聴の報酬は
**画面には正しく表示されるが `RUN_SAVE_KEY` へは一切保存されない**状態になり、報酬を
受け取った直後にタスキルすると雫・復活状態ごと消えていた。

`gRef.current` を同期的に読み、ガード判定後に素の値で `setG` する形(`useItem`/`equipItem`
と同じパターン)に統一して解消。**教訓**: `committed` パターンの是正は「`setG(updater)` を
使っている箇所」だけでなく「そのトリガーが React のイベント系を経由しない外部コールバック
(ネイティブブリッジ・`setTimeout`・`Promise` の then 等)かどうか」も必ず確認すること。

### B-6. レアが最後の1体として時間切れで消えるとソフトロックする(実証済み・BTL-08 テスト作成中に発見)

金枝の精(レア)は `fleeIn` ターンで自動的に消える。この hp=0 化は `enemyPhase`(敵の
ターン)の中で起きるが、「全滅したら reward 画面へ」の判定は `afterPlayerAction`(プレイヤー
の攻撃直後、`enemyPhase` を呼ぶ**前**)の `alive.length === 0` チェックにしか存在しない。
このため、通常の雑魚を先に倒し尽くし、レア1体だけが残った状態でレアを攻撃せずに待つ
(防御・道具使用などレアに直接ダメージを与えない行動を繰り返す)と、レアが時間切れで消えた
瞬間に `phase` が `"battle"` のまま、生存している敵が0体という状態で止まってしまい、
攻撃対象がいないため実質的に何もできなくなる(唯一の進み方は「タイトルへ」で中断すること)。

`enemyPhase` の末尾(状態異常処理・死亡判定の後)に「敵が全員 hp<=0 になったら
`battleWon()` を呼ぶ」処理を追加して解消。`battleWon()` は `gRef.current` を読むため、
`afterPlayerAction` が撃破時に行っているのと同じ手当て(`setG` → `sleep(420)` →
`seqRef` の再確認 → 呼び出し)を踏襲した。`rollDrops()` は元々 `!e.fled` でフィルタして
いるため、この修正後も逃げたレアから雫が出ることはない(意図通り)。
