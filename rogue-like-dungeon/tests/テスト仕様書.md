## 1. この仕様書の使い方

- **IDの付け方**: 領域略号 + 連番(`SAVE-01`, `ITEM-03`…)。実装ファイルは `test<n>_<slug>.js`。`run-all.js` が `test\d+.*\.js` を自動で拾う。
- **優先度**: `P0` = 資産消失・進行不能につながる、リリース前に必ず潰す。`P1` = 仕様乖離・バランス破壊。`P2` = 表示・演出。
- **状態**: `済` = 既存テストで担保済み / `新規` = 未実装 / `手動` = 自動化が割に合わず手順書経由。
- 各ケースの「期待値」は**保存データ(`store`)と画面テキストの両方**で書く。片方だけだと、片方には出ているが保存されていない類のバグを見逃す。

### テストの型(この3つに寄せる)

| 型 | 何を検証するか | 書き方 |
|---|---|---|
| **状態遷移系** | 画面を操作した結果、`g` と保存データが期待通りか | `d.click()` → `d.flush()` → `d.readJSON(KEY)` |
| **再起動系** | 任意の時点でタスキルしても直後に不整合が無いか | `makeDriver()` を作り直し、前の `store` を `d.seed()` し直して再マウント |
| **連打系** | 同一ボタンの多重タップで二重付与・二重消費が起きないか | `d.doubleClickRace()` / `d.raceClicks()`(異なる2ボタンの同時押し) |

**再起動系は全 P0 ケースに必ず1本添えてください。** ユーザーからの不満はほぼタスキルの前後に集中します。

## 4. カバレッジ目標

| 指標 | 目標 | 現状(2026-09-14) |
|---|---|---|
| P0 ケース | 100% 自動化・常時緑線 | **達成**(10/10。`test18`〜`test20`,`test22`〜`test26` 等) |
| P1 ケース | 80% 以上を自動化 | **達成**(12/12 = 100%。`test21`,`test27`〜`test31`,`test34`〜`test36`,`test38` 等) |
| P2 ケース | (目標未設定だったが)自動化できるものは自動化 | 自動化5件すべて実装(`test39`〜`test43`)。手動確認のみ2件(AD-06, UI-04)は元々対象外 |
| 新規バグ修正 | **必ず**再現テストを先に書き、赤を確認してから直す | 今回の拡充作業中に見つかった実バグ(B-5〜B-8)は全てこの手順で修正 |
| 実行時間 | `npm test` 全体で 3 分以内(超えたら並列化を検討) | 実測 約10秒(43ファイル、`run-all.js` は逐次実行のまま余裕あり) |

**このテスト仕様書のケースは全て実装済み**(SAVE〜UI の自動化対象51件中、手動確認専用の
AD-06/UI-04 を除く49件が `test1`〜`test43` でカバーされている)。実装の過程で、静的レビュー
だけでは見つからなかった実バグを4件発見・修正した(詳細は `潜在バグ棚卸し.md` の B-5〜B-8):
- **B-5**: 広告報酬(雫2倍・復活)がネイティブコールバック起因の `committed` パターンで保存スキップ
- **B-6**: レアが最後の1体として時間切れで消えると戦闘画面がソフトロック
- **B-7**: 旧スキーマの中断ラン(`armor` 欠落)再開でアプリ全体がクラッシュ
- **B-8**: 祠の報酬選択(継承枠/精の結晶)が連打で二重付与
